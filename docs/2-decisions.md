## D1 · 역할 경계와 코드 배치

**결정**: 도면을 읽고, 만들고, 검사하는 일은 CAD에 의존하지 않는 Python 엔진이 맡는다. AI는 요구를 해석해 툴을 부르고, MCP는 CAD 연결만 맡는다.

| 구성 요소 | 맡는 일 | 맡지 않는 일 | 실행 환경 |
| --- | --- | --- | --- |
| AI (Claude Code·Claude 앱 + 스킬) | 요구 해석, 작업 계획, 툴 호출, 결과와 가정 보고 | 대량 좌표 계산, 즉석 LISP 작성. 객체 명세에는 배치 규칙(반복·대칭·그리드 기준)을 담고, 좌표는 엔진이 펼친다 | 어디서나 |
| 엔진 (`src/engine`) | 표준 프로파일 읽기, DXF 읽기·요약, 검사, 배치 규칙을 좌표로 펼치기, 객체 명세 → DXF 작성, 변경 목록 계산 | COM·CAD 호출 | Windows, Linux, 클라우드 |
| MCP (`arcaid-cad`) | CAD 연결, 내보내기·삽입·변경 적용·선택·출력·캡처, 엔진 툴 노출 | 기하 계산과 표준 판정(엔진에 맡김) | Windows + 실행 중인 CAD |
| CLI (`arcaid`) | 엔진 툴을 파일 단위로 실행(read, check, build) | CAD 조작 | 어디서나 |
| 스킬 | 작업 절차, 판단 기준, 툴 사용 순서, 보고 형식 | 표준값 보관(표준 파일에서 조회) | AI와 함께 |

**코드 배치**

- `src/engine/`은 ezdxf·pydantic·PyYAML만 쓴다. 테스트에서 `win32com`이 불러와지지 않는지 확인한다.
- MCP(`src/server.py`)와 CLI(`src/cli.py`)는 같은 엔진 함수를 부른다. 같은 입력에 같은 결과가 나오는지 테스트로 묶는다.
- `src/cad_controller.py`(COM 계층)는 MCP만 쓴다.
- 엔진 테스트는 CAD 없이 클라우드에서도 돈다. CAD 연동 테스트는 Windows PC에서 따로 돈다.

**객체 명세의 최소 계약** (세부 JSON은 0단계 실행 계획에서 정한다)

- 단위는 mm, 좌표계는 모형 공간 WCS
- 지원 객체(0-A): 선, 폴리라인, 원·호, 문자, 블록 참조(속성 포함), 해치, 선형 치수
- 배치 규칙: 반복(개수·간격), 대칭, 그리드 축 기준 위치
- 표준 프로파일 ID와 버전, 대상 도면·스냅샷 ID

**이유**: 엔진을 CAD에서 떼어야 같은 입력이면 같은 결과를 테스트로 보장할 수 있고, CLI와 ArcAid로 그대로 옮길 수 있다.

**검토한 대안**: 생성 로직을 LISP로 짜서 CAD 안에서 실행하는 방법. 테스트와 버전 관리가 어렵고 CAD마다 동작이 달라 제외했다.

## D2 · 툴 목록과 결과 형식

**결정**: 현재 툴 39개 중 3개를 정리하고 10개를 새로 만든다. 그리기·편집 툴 23개는 수정과 예외 처리용으로 남긴다. 모든 읽기·검사·적용 결과는 같은 형식을 쓴다.

진행(2026-10-15): T7까지 툴 45개. 0-A 신규 9개와 정리 3개를 반영했다. `apply_changes`는 0-B에서 만든다.

| 구분 | 툴 | 처리 |
| --- | --- | --- |
| 문서 | open\_drawing, save\_drawing, close\_drawing, list\_drawings, switch\_drawing | 유지. `save_drawing`으로 DXF를 저장하지 않는다(D6) |
| 명령 | send\_command, cancel\_command, run\_lisp | 유지 |
| 조회 | list\_layers, list\_entities, get\_entity\_properties, list\_blocks, screenshot | 유지. 몇 개 객체를 확인할 때만 쓴다(D4) |
| 그리기·편집 23개 | draw\_\* 8개, add\_dimension, 편집 9개(erase·move·rotate·scale·copy·mirror·offset·배열 2개), undo, redo, set\_current\_layer, insert\_block, create\_block | 유지. 수정·예외용으로만 쓴다. 보호되지 않는 경로라 태그가 붙은 엔진 객체는 고치지 않는다(D5) |
| 정리 | process\_command | 제거(`nlp_processor`와 함께) |
| 정리 | create\_layer | `ensure_standard_layers`로 대체. 색을 지정하지 못해 표준을 어긴다 |
| 정리 | new\_drawing | `new_from_template`로 대체. 표준 레이어가 없는 빈 도면을 만든다 |
| 신규 · MCP | new\_from\_template | 회사 템플릿으로 새 도면을 열고 지정 경로에 저장 |
| 신규 · MCP | ensure\_standard\_layers | 필요한 표준 레이어를 표준 색·선종류로 만든다 |
| 신규 · MCP | export\_snapshot | 열린 도면을 DXF 사본으로 내보낸다. 문서 이름은 그대로 둔다(D6) |
| 신규 · MCP | draw\_batch | 객체 명세(JSON)를 받아 엔진이 DXF를 쓰고, 열린 도면에 삽입한 뒤 검사 결과를 돌려준다 |
| 신규 · MCP | apply\_changes | 0-B 단계. 이동·삭제·속성 변경 목록을 적용 직전 확인을 거쳐 적용한다(D5) |
| 신규 · MCP | get\_selection | 사용자가 CAD에서 고른 객체의 핸들과 요약 |
| 신규 · MCP | plot | 지정한 범위나 레이아웃을 PDF로 출력 |
| 신규 · 엔진 | read\_drawing | DXF 사본을 구조화된 요약으로 읽는다(D4) |
| 신규 · 엔진 | check\_standard | 표준 검사. 레이어·색처럼 정답이 정해진 위반은 고칠 목록도 만든다. MCP에서 부르면 바로 고칠 수 있다 |
| 신규 · 엔진 | get\_standard | 표준 프로파일 조회(레이어 용도, 문자 높이 등) |

**결과 형식**: 읽기·검사·적용 툴의 결과에는 아래 항목을 둔다.

- `status`: 성공, 충돌, 실패, 복구 완료, 확인 불가 중 하나
- `summary`: 한 줄 요약
- `scope`: 이번 요청의 대상과 지원 범위
- `checked`: 처리하거나 검사한 항목과 개수
- `violations` 또는 `applied`: 위반 목록(위치·핸들) 또는 적용 내역
- `unchecked`: 요청 범위 안에서 처리하거나 검사하지 못한 항목과 이유
- `out_of_scope`: 처음부터 범위에서 뺀 항목(예: 0단계의 벽체 인식)
- `assumptions`: 기본값으로 가정한 값
- `ids`: 요청 ID, 도면·스냅샷 ID, 표준·스키마 버전

`status`가 성공이고 `unchecked`가 비어 있을 때만 '완료'로 보고한다. `out_of_scope`는 완료 판정에 넣지 않는다. 스킬의 보고 형식도 이 항목을 따르고, 세부 JSON은 0단계 실행 계획에서 정한다.

## D3 · 표준 파일

**결정**: 회사 표준을 YAML 표준 프로파일로 만들어 레포에 둔다. MCP, CLI, 검사기가 모두 이 파일을 읽고, 스킬 문서는 표준값을 직접 적지 않는다.

**위치와 구성**: `standards/heo-2026/` 폴더 하나가 프로파일 하나다. 다른 사무소 표준도 같은 구조로 추가할 수 있다.

| 파일 | 담는 내용 |
| --- | --- |
| `profile.yaml` | 이름, 버전, 기준 템플릿(`회사표준_템플릿.dwg`), 축척 규칙(A3 축척 분모 k, s = k/100, DIMSCALE = k/2, LTSCALE = k). 주석 축척은 쓰지 않는다 |
| `layers.yaml` | 표준 레이어 40개의 이름, 색(출력 선굵기), 선종류, 용도. 필요하면 허용 객체 종류 |
| `text.yaml` | 문자 스타일(돋움)과 용도별 높이(A3 1/100 기준값) |
| `dimensions.yaml` | 치수 스타일(DIM330, DIM270, 비주석), 축열·치수·버블 간격 |
| `blocks.yaml` | 표준 블록(축열 버블, 계단 화살표, 절단선, 레벨, 도곽)의 이름, 삽입 레이어, 속성, 배율 규칙 |

**단일 원본 유지**

- 형식은 pydantic 모델로 검증한다. 표준 버전과 스키마 버전을 따로 둔다.
- 기준 템플릿의 해시를 `profile.yaml`에 적는다.
- 템플릿과 YAML이 레이어·문자 스타일·치수 스타일·블록 정의에서 같은지 테스트로 확인한다. 다르면 작업을 멈추고 보고한다.
- 대상 도면에 같은 이름의 레이어·스타일·블록이 표준과 다른 정의로 있으면 덮어쓰지 않고 멈춘 뒤 보고한다. 고칠지는 사람이 정한다.
- 스킬 `references`의 표는 YAML에서 생성하거나 `get_standard`로 조회한다. 손으로 고치지 않는다.

**주석 축척**: 쓰지 않는다. 사내 작업이 주로 비주석이고, 스킬 규칙(표준값 × s, DIMSCALE = k/2)도 비주석을 전제로 한다. 템플릿의 DIM330·DIM270이 주석 스타일이면 비주석으로 바꾸고, 표준매뉴얼과 스킬도 함께 고친다. 엔진이 만든 객체가 주석 축척이면 검사기가 위반으로 잡는다. 기존 도면의 주석 객체는 읽어서 표시만 한다.

옛 템플릿으로 만든 프로젝트 도면에는 주석 DIM330 정의가 남아 있을 수 있다. 이런 도면에 생성 DXF를 삽입하면 대상 도면의 정의가 우선해 새 치수가 주석 치수가 된다. 위의 '같은 이름, 다른 정의' 규칙이 이 경우를 막는다.

T0(E1·E5) 확인: 지금 템플릿의 DIM330·DIM270은 주석 스타일이고, 1/100(주석 축척 1:100)에서 치수 문자가 330으로 표준 165의 2배가 된다. LISP `entmod`로 치수 스타일의 `AcadAnnotative` XDATA를 지우면 비주석이 되고 DIMSCALE 50·100에서 165·330이 나온다. 대상 도면에 다른 정의의 DIM330이 있으면 넣은 치수가 다시 계산될 때 대상 정의를 따른다(165→250). 그래서 아래 '같은 이름, 다른 정의' 규칙을 지킨다.

**0단계 범위**: 레이어, 문자, 치수, 블록, 도곽. 해치 패턴과 출력 설정 파일(CTB)의 내용은 제외한다. `plot`은 CAD에 설치된 회사 CTB를 이름으로 지정해 출력하고, 이 출력이 정식 출력과 같은지는 0단계에서 확인한다.

**이유**: 지금은 표준값이 스킬 마크다운에만 있어 코드가 읽지 못하고, 검사를 AI가 해야 한다. YAML은 사람이 읽고 고치기 쉽고, 바뀐 내용을 git diff로 확인할 수 있다.

## D4 · 도면 읽기

**결정**: 도면은 DXF 사본으로 읽는다. COM 조회는 몇 개 객체를 확인할 때만 쓴다. 0단계 판독은 표준 레이어로 그린 그리드와 실명까지다.

**경로**

- 열린 도면: `export_snapshot`으로 DXF 사본을 만들고 `read_drawing`이 읽는다. 저장하지 않은 변경이 있을 수 있어 매번 새로 내보낸다. 원본이 CAD에 열려 있으면 디스크 파일이 아니라 열린 문서를 내보낸다.
- 닫힌 파일: CAD로 열어 내보낸다(D6). 경로·수정 시각·크기가 같으면 이전 사본을 다시 쓰되, 읽기에만 쓴다. 변경을 적용할 때의 기준은 항상 새 스냅샷이다.

| 범위 | 내용 | 대상 도면 |
| --- | --- | --- |
| 추출 | 모형 공간 객체의 종류·레이어·색·선종류·핸들, 블록 참조(이름·삽입점·배율·회전·속성값), 문자 내용·높이, 치수 측정값, 단위(`$INSUNITS`)와 도면 범위, Xref 목록과 경로 | 모든 도면 |
| 판독 | 그리드: `CEN` 레이어 축선과 축열 버블 블록의 속성값. 실명: `ROM` 레이어의 문자와 위치 | 표준 레이어로 그린 도면 |
| 범위 밖 | 레이아웃, Xref 내부 객체, 블록 정의 내부(표준 블록 정의 비교는 D3), 벽 쌍선에서 벽체 인식, 창호·문 종류 판별, 비표준 레이어 도면의 의미 해석 | `out_of_scope`로 표시 |

**출력**: JSON 요약. `meta`(원본·사본 경로, 단위, 범위, 내보낸 시각, 스냅샷 ID), `layers`(레이어별 개수, 비표준 레이어), `grid`(축 이름·좌표), `rooms`(실명·위치), `blocks`, `xrefs`, 그리고 D2의 공통 항목(`status`, `unchecked`, `out_of_scope` 등).

**단위**: 읽기에서는 단위가 mm가 아니면 경고한다. 변경을 적용할 때는 단위가 정해지지 않았거나 블록 배율로 단위가 섞이면 적용하지 않는다(D5). 확인된 단위는 mm로 바꾼 뒤 허용오차를 적용한다. 당산동 작업에서 m/mm 불일치를 겪었다.

**이유**: 당산동 평면 작업에서 DXF를 ezdxf로 읽는 쪽이 `list_entities`보다 정확했다. COM 조회는 객체 수만큼 호출이 늘어난다. ezdxf는 DXF를 다루는 도구일 뿐 건축 객체를 해석하지 않으므로, 판독 규칙을 따로 만들고 범위를 좁혀 시작한다.

## D5 · 변경 적용

**결정**: 엔진이 만든 객체에는 XDATA로 지속 ID를 붙인다. 보호된 적용 경로(`draw_batch`, `apply_changes`)는 '적용 직전 확인 → Undo 그룹 안에서 적용 → 결과 확인 → 검사 → 보고' 순서를 따르고, 확인을 통과하지 못하면 아무것도 바꾸지 않는다.

&#91;embedded content: 변경 적용 흐름 · 5단계, 확인 2곳\]

적용 직전 확인에서 하나라도 다르면 바로 멈추고, 적용 중 실패하면 Undo를 실행하고 원래 상태로 돌아왔는지 확인한다. 어느 경우든 결과는 D2의 결과 형식으로 보고한다.

**0단계 적용 범위**

- 0-A: 새 객체 추가(`draw_batch`)와 표준 위반의 레이어·색 수정(`check_standard`). 레이어·색 수정은 기존 객체를 고치는 가장 작은 경우라, 수정 경로 전체를 작게 시험하는 역할도 한다.
- 0-B: 기존 객체의 이동·삭제·속성 변경(`apply_changes`). 대상은 우선 선·폴리라인·문자·블록 참조로 한정하고, 0-A 검증을 통과한 뒤 시작한다. 세부: [0-B 실행 계획](4-phase0b-plan.md)(2026-10-17).
- 저수준 그리기·편집 툴과 `send_command`·`run_lisp`는 보호되지 않는 경로다. 결과에 그 사실을 표시하고, 태그가 붙은 엔진 객체는 이 경로로 고치지 않는다.

| 장치 | 규칙 |
| --- | --- |
| 식별 | 요청은 `op`(요청 ID)와 입력 명세 해시로 식별한다. 객체는 도면 ID와 지속 객체 ID(`oid`)로 식별하고, 층·실 같은 의미 경로(`path`)는 별도 속성으로 둔다. 문처럼 여러 CAD 객체로 이루어진 것은 의미 객체 ID와 구성 객체 ID를 나눈다 |
| 태그 | XDATA 앱 이름 `ARCAID`. `op`, `oid`, `path`, `ver`(엔진 버전), `in`(입력 명세 해시), `state`(기준 상태 해시)를 문자열(1000번 코드)로 저장한다. `state`는 도면에 넣은 뒤 단다 |
| 기준 상태 | 삽입이 끝난 뒤 CAD 안의 최종 객체에서 읽어 저장한다. 비교 항목은 객체 종류별로 정한다. 공통은 레이어·색·선종류, 문자는 위치·높이·정렬·스타일·내용, 블록 참조는 삽입점·배율·회전·블록 이름·속성값, 치수는 정의점·스타일·덮어쓰기 값이다. 보호된 경로로 정상 변경했을 때는 기준 상태도 함께 갱신한다 |
| 적용 직전 확인 | 대상마다 읽을 때의 상태를 담고, 적용 직전에 다시 읽어 0.01mm 허용오차로 비교한다. 활성 도면과 단위도 확인한다. 하나라도 다르면 전체를 멈춘다 |
| 재실행 | 같은 `op`, 같은 입력, 예상 객체가 모두 있을 때만 건너뛴다. 같은 `op`에 다른 입력이면 충돌이다. 일부만 있으면 완료로 보지 않고 멈춘 뒤 보고한다. `replace`도 충돌 검사를 거치며, 사람이 고친 객체가 섞여 있으면 멈춘다 |
| 수동 수정 감지 | 현재 상태가 `state`와 다르면 사람이 고친 것으로 보고 덮어쓰지 않는다. 같은 `oid`가 둘 이상이면(복사) 충돌로 보고한다 |
| 되돌리기 | 예외나 결과 확인 실패 때 Undo 그룹을 닫고 실제 Undo를 실행한 뒤, 적용 전 상태로 돌아왔는지 확인한다. 확인하지 못하면 `status`를 '확인 불가'로 보고한다. 새로 생긴 검사 위반은 되돌리지 않고 보고한다. 타임아웃·연결 끊김·사용자 취소 뒤에는 후속 변경을 멈춘다 |
| 추가 경로 | 엔진이 임시 DXF를 쓰고 MCP가 열린 도면에 삽입·분해한다. 검증에 실패한 객체 종류는 COM·LISP로 직접 만든다 |

**T0 결과 반영** (2026-10-14, [사전 검증 결과](https://github.com/planetai87/arcaid-cad/blob/main/docs/spike-report.md))

- 추가 경로: 생성 DXF는 COM `Document.Import`로 넣는다. 레이어·색·선종류·한글·블록 속성·XDATA가 보존된다. Import는 단위를 환산하지 않으므로 적용 전에 대상 단위가 mm인지 확인한다.
- 생성 DXF에는 대상 도면에 없는 정의만 담는다. 템플릿 전체를 담으면 넣는 데 6초, 레이어만 담은 DXF는 객체 1,000개에 0.06초였다. 같은 이름의 정의는 어차피 대상 것이 남는다.
- 되돌리기: 묶음 안에 다른 Undo 묶음이나 명령(입력 대기·취소 포함)이 끼면 `UNDO 1`이 복귀하지 못했다. 보호된 경로는 묶음 안에서 COM 호출만 쓰고, 복귀는 핸들 집합으로 확인한다. 복귀하지 못하면 0-A는 추가만 하므로 `op` 태그로 찾아 지우고 남은 것이 없는지 확인한다(검증함).

**현재 코드와의 차이**: 지금 `_undo_group`은 StartUndoMark와 EndUndoMark로 작업을 묶기만 한다. 실패 시 자동 Undo와 복귀 확인은 없고, EndUndoMark 실패도 무시한다. 위 '되돌리기'는 0-A에서 새로 만든다. 적용 전 스냅샷 DXF와 저장 때 생기는 .bak은 비교·참고 자료일 뿐, 저장하지 않은 최신 상태를 완전히 복구하는 수단이 아니다. T6에서 보호된 경로(`draw_batch`·`fix`)에 실패 시 Undo와 핸들 집합 복귀 확인, 태그 지우기 대안을 만들었다. 저수준 툴의 `_undo_group`은 그대로다.

**이유**

- 도면을 삽입하거나 Xref를 바인드하면 핸들이 새로 붙는다. Autodesk 문서도 다른 도면의 객체를 가리킬 때 핸들 대신 문자열을 권한다. 핸들만으로는 엔진 객체를 추적할 수 없다.
- XDATA는 객체 자체에 붙어 있어 이동·회전에도 유지되고, LISP `entget`로 바로 읽힌다. AutoCAD는 객체당 16KB까지 허용한다.
- 태그 하나로 재실행 판정, 사람 객체와의 구분, 수동 수정 감지를 함께 처리한다.

## D6 · DWG·DXF 변환과 작업 파일

**결정**: DWG와 DXF 사이 변환은 CAD(GstarCAD)로 한다. ODA File Converter는 ODA가 비회원에게 비상업적 용도만 허용한다고 밝히고 있어, 이용 계약이 사내 사용·자동화 방식에 맞는지 확인하기 전에는 쓰지 않는다. 내보내기 방법과 출력 버전은 아래 실험 결과로 정한다.

**열린 도면 내보내기**: 지금 `save_drawing`은 SaveAs 방식이라, DXF로 저장하면 열린 문서가 그 DXF 파일로 바뀔 수 있다. 그 뒤 저장하면 원본 DWG 대신 DXF에 저장되는 위험이 있다. 문서 이름을 바꾸지 않는 방법을 0단계에서 검증해 하나를 고른다.

1. COM `Export`(.dxf): AutoCAD 문서상 DXF는 선택 세트와 관계없이 도면 전체를 내보낸다. 버전 인자가 없으므로 출력 버전(R2013)과 GstarCAD에서의 동작을 따로 확인한다.
2. `-WBLOCK`으로 도면 전체를 별도 DWG로 쓴 뒤, 그 파일을 열어 R2013 DXF로 저장하고 닫는다.
3. `DXFOUT`: 실행 뒤 문서 이름·경로·수정 상태가 유지되는지 확인하고, 그 결과로 순위를 정한다.

후보는 같은 기준으로 비교한다. 원본 문서 이름·경로와 저장하지 않은 수정 상태 유지, 출력 DXF 버전, 공간·객체·스타일 보존, Xref 경로와 단위 보존, 실패 때 원본과 활성 문서의 상태, 소요 시간이다.

**T0 결과(2026-10-14)**: 열린 도면 스냅샷은 COM `Export(이름, "DXF", 빈 선택 세트)`로 만든다.

- Export: 문서 이름·경로·미저장 상태와 활성 문서를 유지하고, 데이터·한글·블록 속성이 일치하며, 핸들이 100% 같다(0.3초). 출력은 R2018(AC1032)이다. 파일 이름에 `.dxf`를 붙이면 실패하므로 확장자 없이 준다.
- `-WBLOCK`·COM `Wblock`: R2013을 내지만 핸들이 하나도 맞지 않고 3초 걸린다.
- `DXFOUT`: R2013·핸들 일치지만 저장하지 않은 도면을 '저장됨'으로 바꿔, 사용자가 저장 안내 없이 닫을 수 있다. 쓰지 않는다. 실패해도 오류 신호가 없어 파일 존재로만 알 수 있다.
- SaveAs로 DXF를 쓰면 열린 문서가 그 DXF로 바뀐다(확인). `save_drawing`으로 DXF를 저장하지 않는다.

**닫힌 파일과 일괄 변환**: MCP가 CAD에서 파일을 열어 내보내고 닫는다. 사용자가 열어 둔 도면과 섞이지 않게 처리하고, 끝나면 원래 활성 도면으로 돌아온다. 속도가 문제가 되면 ODA 회원 가입이나 다른 변환기를 그때 검토한다.

**형식과 경로**

- 엔진이 쓰는 생성 DXF는 R2013으로 고정하고, 스냅샷(CAD가 내보낸 읽기용 사본)은 R2013 이상(AC1027·AC1032)을 받는다. 한글 문자열은 내보내기·삽입 왕복에서 그대로 유지됐다(T0).
- 생성은 회사 템플릿을 변환한 `template.dxf` 위에서 한다. 표준 레이어·스타일·블록 정의가 들어 있다.
- 작업 폴더는 전체 경로에 한글과 공백이 없는 로컬 경로로 따로 지정하고(예: `C:\arcaid\work`), 시작할 때 검사한다. 지금 설정된 출력 폴더 경로에는 공백이 있다. LISP가 한글 경로를 못 다룰 수 있어 `run_lisp`도 이미 영문 경로를 쓴다. T0에서 한글·공백 경로도 COM 열기·저장, -INSERT, Import, Export, LISP open이 모두 동작했다. 그래서 영문 경로는 기본값으로 두되 막는 조건으로 쓰지 않는다.
- 원본 DWG는 CAD만 저장한다. DXF는 사본과 추가분 전달용으로만 쓴다.

## D7 · 대상 CAD와 호환 범위

**결정**: GstarCAD 2021을 기준으로 개발하고 검증한다. BricsCAD는 같은 검증 목록으로 호환을 확인하고, AutoCAD와 ZWCAD는 코드 경로만 유지한다.

| CAD | 상태 | 처리 |
| --- | --- | --- |
| GstarCAD 2021 | 기준 | 아래 검증 목록 통과가 0단계 통과 조건 |
| BricsCAD | 호환 확인 | 동료 PC에서 검증 중. 같은 검증 목록을 다시 돌린다 |
| AutoCAD | 미검증 | 코드 경로만 유지. 결과에 '미검증'을 표시한다 |
| ZWCAD | 미검증 | AutoCAD와 같다 |

CAD마다 다른 동작은 `cad_controller`에서만 나눠 처리하고, 엔진은 CAD 종류를 모른다. 이미 알려진 차이(예: GstarCAD는 COM 해치가 화면에 그려지지 않아 `-HATCH` 명령을 쓴다)는 호환표로 남긴다.

BricsCAD는 검증한 버전과 환경을 기록한다. 결과에는 엔진 검사 결과와 CAD 연결부의 호환 상태를 따로 적는다.

## D8 · 도면 데이터의 외부 AI 전송 범위

**결정**: A안(제한 없음, 2026-10-14 사용자 결정). 경로·문자 내용·실명·블록 속성·도곽 정보·화면 캡처를 모두 AI에 보낸다. 단 `run_lisp` 결과 안의 파일 경로는 가린다. 필터는 `config/egress.yaml`의 항목별 정책으로 동작해, B안으로 바꿀 때는 코드 수정 없이 설정만 바꾼다. 남은 확인: 사용 중인 Claude 요금제의 데이터 처리 조건(학습 사용, 보관 기간)과 비밀유지 계약 건은 사용자가 확인해 이 문서에 적는다.

아래 표와 B안의 경계 규칙은 검토한 안이다(권장안이었던 B안으로 바꿀 때 따를 규칙).

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 제한 없음 | 도면 사본, 요약, 화면 캡처를 모두 AI로 보낸다 | 가장 편하다 | 건축주 도면이 그대로 외부로 나간다 |
| B. 허용 목록 (권장) | 도면은 로컬 엔진이 읽는다. MCP가 AI에 돌려주는 결과에는 허용한 필드만 담고, 확인되지 않은 데이터는 보내지 않는다. 화면 캡처는 별도 절차로 다룬다 | D1·D4 구조와 맞고, 보내는 범위를 미리 정할 수 있다 | 허용할 필드를 정하고 관리해야 한다 |
| C. 사내 작성 도면만 | 회사가 작성한 도면만 쓰고, 건축주 제공 도면은 쓰지 않는다 | 외부 도면의 노출이 줄어든다 | 사내 도면에도 건축주·프로젝트 정보가 있어 위험이 사라지지 않는다. 용도변경·기존 건물 작업에 쓰기 어렵다 |

**B안의 경계 규칙**

1. MCP 결과가 AI로 돌아가는 시점을 외부 전송 경계로 본다.
2. 상세 데이터(경로, 문자 내용, 블록 속성 등)는 PC 안의 로컬 결과에 두고, AI에 돌려주는 결과에는 허용 목록의 필드만 담는다.
3. 파일 경로·파일명, 문자 내용, 실명, 블록 속성, 도곽 정보는 건축주·프로젝트 정보를 담기 쉽다. 이 항목들의 허용 여부는 사무소가 항목별로 정한다.
4. 화면 캡처는 범위를 지정하고, 보내기 전에 확인하는 절차를 둔다.
5. 허용 여부가 정해지지 않은 데이터는 보내지 않는다.

어느 안이든 두 가지를 함께 정한다.

- 사용 중인 Claude 요금제의 데이터 처리 조건(학습 사용 여부, 보관 기간)을 확인해 이 문서에 기록한다.
- 계약서에 비밀유지 조항이 있는 건은 따로 확인한다.

## D9 · IR과 수동 편집

**현재 원칙(확정 대상)**: 2단계 전까지 DWG가 형상의 기준이다. 사람이 고친 엔진 객체는 덮어쓰지 않고 충돌로 보고한다(D5).

**보류**: IR을 원본으로 바꾸는 일과 양방향 편집 정책은 2단계 진입 전에 정한다.

**0단계에서 준비할 것**

- 엔진 객체의 지속 ID(`oid`)와 의미 경로(`path`)를 나눠 두어, 나중에 IR 객체와 대응시킬 수 있게 한다.
- 태그 값을 IR ID로 그대로 쓰기로 지금 정하지는 않는다. 대응 관계를 유지할 수 있으면 충분하다.

**2단계 진입 전에 정할 질문**

1. CAD에서 손으로 고친 형상과 IR이 다르면 어느 쪽을 기준으로 삼는가.
2. 손으로 고친 객체를 다시 생성할 때 유지·갱신·충돌 보고 중 무엇으로 처리하는가.
3. 엔진 객체와 사람 객체를 어떻게 구분하는가. 0단계 태그로 대부분 풀리고, 태그가 지워진 경우가 남는다.
4. IR에 반영할 수 없는 변경을 어떻게 표시하고 처리하는가.
