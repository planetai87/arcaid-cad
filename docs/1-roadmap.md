# arcaid-cad 로드맵

Oct 14, 2026 · @Jeonglo Choi

arcaid-cad를 사내 실무자가 쓰던 CAD 안에서 AI와 함께 도면을 만들고 검토하는 설계자동화 도구로 키운다. 0단계 기반 정비 뒤 계획설계, 인허가 도서, 실시설계 보조, 3D 연계 순으로 넓힌다. 각 단계는 그 자체로 실무에 쓰일 때만 다음 단계로 넘어간다.

## 목표와 범위

사내 실무자가 쓰던 CAD를 그대로 쓰면서, AI가 반복 작도와 검토를 맡아 실무 결과물의 생산성을 높인다. 새 프로그램을 배우지 않아도 되는 것이 도입의 전제다.

**만드는 것**

- 계획설계 보조: 규모검토, 법규분석, 대안 비교
- 기본설계: 기본도면을 바탕으로 인허가 도서 세트를 만들고 반복 검토
- 실시설계 보조: 일람표, 상세도 배치, 도면 간 정합성 검사
- 이후 연계: SketchUp·Rhino 모델링, 렌더링

**만들지 않는 것**

- 자체 CAD 커널과 편집 화면. 표시와 편집은 GstarCAD 등 기존 CAD가 맡는다.
- 범용 웹 CAD와 별도 승인 화면. 다만 AI가 만든 명세를 보고, 가리켜 지적하고, 값을 직접 고치는 로컬 검토·수정 도구는 둔다(2026-10-31). 이 도구는 CAD에 붙지 않고, 최종 확인은 CAD 안에서 한다. 외부용 웹 화면은 ArcAid 서비스로 낼 때 다시 판단한다.
- 실시설계 완전 자동화. 시공 지식과 책임 문제 때문에 반복 작업 보조로 한정한다.
- 설계 판단의 자동화. 판단은 건축가가, 작도와 검증은 도구가 맡는다.

**0단계 착수 때 확인한 공백** (당산동 숙박시설 기준층 평면 작업과 코드 검토 기준)

- 생성 로직이 일회용이다. 객실 27개, 객체 943개를 즉석 Python→LISP로 그렸고, 다음 건에서 다시 짜야 한다. → 객체 명세 + draw_batch(T5·T6)
- 그리기 툴은 대량 작업에 맞지 않는다. 실제로 쓴 것은 열기·저장·`send_command`였다. → draw_batch·apply_changes

- 표준값이 마크다운에만 있어 코드가 읽지 못한다. → YAML 표준 프로파일(T2)
- 겪은 함정이 코드에 남지 않았다. m/mm 단위 불일치, 주석 축척 치수(DIM330), 1/200 문자 겹침. → 단위·치수 스타일 검사 규칙과 시험(T2·T4)
- 벽 두께, 문·창 크기가 AI의 가정이었다. 표준과 프로젝트 입력에서 와야 한다. → 미등록 설계 가정으로 보고, 프로파일 확장은 후속
- 원본 저장소에서 남은 `process_command`·`nlp_processor`가 있고, 테스트가 없다. → 정리(T1), 시험 896개

## 구조와 원칙

요구 해석과 대화는 AI가 하고, 도면은 결정적인 코드(엔진)가 만든다. AI 모델을 바꾸거나 빼도 같은 입력이면 같은 도면이 나와야 한다.

&#91;embedded content: 구성도 · 8개 구성 요소와 호출 방향\]

건축가는 CAD와 채팅 두 곳에서 일하고, AI는 MCP나 CLI를 거쳐 엔진을 부른다. 엔진은 DXF 사본으로 읽고 추가분을 넘기며, DWG 원본은 늘 CAD가 저장한다.

- **스킬은 연구실, 엔진은 제품**: 스킬로 실무를 처리하며 방법을 찾고, 검증된 작업은 엔진 코드와 고수준 툴로 굳힌다.
- **대화형과 배치 두 모드**: 직원이 열어둔 도면은 MCP로, 도서 세트 생성과 일괄 검사는 CLI로 처리한다. 둘은 같은 엔진을 부른다.
- **표준과 프로젝트 조건은 파일로**: 표준값은 `layers.yaml` 같은 기계용 파일에, 프로젝트 조건은 `project.yaml`에 둔다. 스킬과 코드가 같은 원본을 읽는다.
- **DWG가 형상의 기준**: DWG 원본은 CAD가 저장한다. DXF는 읽기용 사본과 추가분 전달용이며, 기존 도면을 DXF로 통째 덮어쓰지 않는다. 작업 전에는 현재 도면을 다시 읽어 직원이 손으로 고친 내용을 반영한다.
- **엔진 객체는 태그로 구분**: 엔진이 만든 객체에는 XDATA 태그를 단다. 중복 실행 방지, 사람이 그린 객체와의 구분, 수동 수정 감지에 쓴다.
- **IR은 엔진 범위부터**: IR은 엔진이 만든 범위에만 쓴다. 수동 편집과 충돌할 때의 처리 원칙을 정한 뒤에 범위를 넓힌다.
- **검토는 CAD 안에서**: 제안안은 별도 레이어, 변경은 색으로 구분한다. 건축가 의견은 `_REVIEW` 레이어의 리비전 클라우드로 받는다.
- **편집마다 자동 검사**: 편집 툴은 결과와 함께 검사 결과를 돌려준다. 위반이 0이거나 사람의 판단이 필요한 항목만 남으면 멈추고, 검사하지 못한 항목과 함께 보고한다. 위반 0이 검토 완료를 뜻하지는 않는다.
- **형상은 기준 파일, 주석은 시트**: 시트는 기준 파일을 Xref(상대 경로)로 참조한다. 기준 파일을 고치면 참조하는 시트를 모두 다시 검사한다.

## 단계별 로드맵

0단계를 마쳤고(BricsCAD 호환은 보류), 1단계 진입 전 결정을 기다린다. 각 단계는 과거 실무 건을 테스트 세트로 삼아 통과 기준을 확인한 뒤 다음으로 넘어간다. 기간은 0단계의 실제 진행 속도를 보고 정한다.

&#91;embedded content: 로드맵 · 5단계와 통과 기준 4개\]

단계 사이의 ◆가 통과 기준이다. 단계별 확인 사례와 평가 항목은 아래 '단계별 통과 기준' 표에 있다.

### 0단계 · 기반 정비 (arcaid-cad·스킬 개선)

- 표준값(레이어·문자·치수·블록)을 기계용 파일로 옮긴다.
- `check_standard`: 표준 검사를 코드로 하고 위반 목록과 위치를 돌려준다. 검사하지 못한 항목도 함께 보고하고, 정답이 정해진 위반(레이어·색)은 자동으로 고친다.
- `read_drawing`: DWG를 DXF 사본으로 읽어 객체·속성·단위를 추출한다. 그리드·실 판독은 회사 표준 레이어로 그린 도면까지만 하고, 비표준 도면 해석은 이후로 미룬다.
- `draw_batch`: 객체 수백 개를 표준에 맞춰 한 번에 만든다. 임시 DXF를 만들어 열린 도면에 삽입하는 방식을 우선 검증하고, 실패한 객체는 CAD 직접 조작(COM·LISP)으로 처리한다.
- 원본 보호: 엔진이 만든 객체에 XDATA 태그를 단다. 적용 직전에 대상이 바뀌지 않았는지 확인하고, 같은 요청을 다시 실행해도 중복되지 않게 하며, 실패하면 되돌린다.
- MCP 연결 툴 추가: 내보내기, 병합, 선택 객체 읽기, 출력.
- 엔진을 `src/engine`으로 분리하고 CLI를 연다. 레거시를 정리하고 테스트를 만든다. 스킬은 새 툴 기준으로 고친다.
- 먼저 검증할 것: DXF 왕복(R2013 이상, 한글, 주석 축척 치수, 블록 속성, 해치), DXF 사본과 DWG의 핸들 일치, 삽입 후 XDATA 태그 유지, ODA 자동 변환, GstarCAD의 DXF 삽입.

완료: 2026-10-18. 0-A(T0~T10, 당산동 기준층 평면 재현)와 0-B(B0~B5, 기존 객체 이동·삭제·속성 변경) 통과. BricsCAD V26 호환(B6)은 보류. 남은 후속: 표준 프로파일 확장(상세 블록 등록, PAK1·TXT1 문자 용도), 타원, LTSCALE 맞추기 툴, 표준매뉴얼 DWG 개정 반영, draw_batch 명세 파일 입력(spec_path).

### 1단계 · 계획설계 보조

- `project.yaml`: 대지, 건축 개요, 설계 기준. 값을 입력값(parcel-doser 조회), 산출값(도면에서 계산), 법정값(법규)으로 나누고 출처와 조회 시점을 남긴다.
- 규모검토: 건폐율·용적률·사선 제한·지구단위계획을 반영한 최대 규모와 매스, 대안 비교.
- 법규분석: 용도변경 검토 스킬과 법령 검색을 연결한다. 결과는 자동 판정, 담당자 판단, 미확인 항목으로 나눈다.
- 스키매틱 작도 규칙: 실 경계는 닫힌 폴리라인, 실명은 그 안의 문자. 2단계의 입력이 된다.
- 용도변경 검토와 신축 매스 검토 중 무엇을 먼저 할지는 1단계 진입 시점의 실무 건을 기준으로 정한다.

### 2단계 · 기본설계: 인허가 도서 세트

기본 인허가 도면 세트를 첫 사례 1건으로 끝까지 만든다. 첫 사례(공사 유형·조건)는 2단계 진입 전에 그때의 실무 건을 보고 정한다.

- 기본 세트: 건축개요·면적표, 배치도, 층별 평면도, 입면도·단면도, 주차계획도, 피난·방화구획도, 장애인 편의시설 계획도, 도곽·도면목록. 입면·단면 변경이 없는 건은 '현황 유지'로 표시해 세트를 채운다.
- 첫 사례가 용도변경이면 기존 도면 정리 단계가 들어간다. 레이어 대응표로 표준 레이어에 맞추고 사람이 확인한다.
- IR은 이 작업에 필요한 범위만 다룬다. 건물 전체 IR 전환은 완료 조건이 아니다.

중간 완료 지점:

1. 기준층 평면(신축은 스키매틱에서 생성), 실 목록, 면적표를 만들고 서로 맞는지 확인한다.
2. 기준 파일·시트·도곽·도면목록 구성과 출력을 확인한다.
3. 입력 조건을 제한한 입면·단면을 만든다. 층고·창대 높이처럼 평면에 없는 값은 `project.yaml`에서 받는다.
4. 기본 세트 전체를 완성하고 변경 전파(기준 파일 수정 → 시트 재검사·주석 수정)를 검증한다.

### 3단계 · 실시설계 보조

- 창호·마감 일람표, 사내 상세도 라이브러리 배치, 도면 목록, 도면 간 정합성 검사.
- 시공 판단이 필요한 상세는 사람이 그린다.

### 4단계 · 3D·렌더링 연계

- IR에서 SketchUp·Rhino 모델을 만들고 IFC로 내보낸다. 렌더링은 그 모델에서 한다.
- IR이 안정된 뒤 내보내기 모듈로 붙인다.

작업 시간은 과거 건의 기준 시간을 먼저 재고, 생성뿐 아니라 수정·검토·출력 시간을 포함한다. 수치와 테스트 세트는 0단계 실행 계획에서 정한다.

## 도구 구성과 도입 시점

CLI는 0단계 후반, 검사와 읽기가 CAD 없이 DXF만으로 돌아갈 때 연다. IR은 2단계에 도입하고, 별도 에이전트는 2단계가 끝난 뒤 판단한다.

| 구성 요소 | 역할 | 도입 시점 |
| --- | --- | --- |
| 스킬 (cad-drawing-standard 등) | 작업 절차, 판단 기준, 툴 사용법 | 지금. 툴이 늘수록 절차 중심으로 줄인다 |
| MCP arcaid-cad: 그리기 툴 | 선·문자 단위 작도, 예외 수정 | 지금. 비중을 줄여 수정용으로 남긴다 |
| MCP arcaid-cad: 연결 툴 | 열린 도면 내보내기·병합, 선택 객체 읽기, 출력, 캡처 | 0단계 |
| 엔진 (`src/engine`) | 읽기, 생성, 검사, 변경 목록 계산 | 0단계부터 단계마다 확장 |
| CLI | 일괄 생성·검사, 테스트, Claude Code에서 직접 실행 | 0단계 후반 |
| IR (건물 모델) | 엔진이 만든 범위의 건물 정보. 형상의 기준은 DWG로 두고, 수동 편집 충돌 원칙을 정한 뒤 넓힌다 | 2단계, 필요한 범위만 |
| Claude Code 서브에이전트 (plan-reviewer·plan-reader) | 미리보기 DXF 검토(지적만 함), 평면 이미지 영역별 측정(측정 도구로만 기록, 해석하지 않음). cad-applier는 보류: 메인이 ops 검사·묶기(`tools/ops`) 뒤 `draw_batch(spec_path)`로 적용 | 지금. 아래 Agent SDK 별도 에이전트와 다르다 |
| 이미지 판독 도구 (`tools/raster`) | 평면 이미지 좌표 보정·선 측정, 측정 기록(measure.yaml), 범용 생성기(측정 기록 → ops), 원본 겹침 | 지금. 입력은 CAD에서 내보낸 PNG와 사진(다항식 휨 보정, 오차 수십 mm). 원근이 큰 사진과 벡터 PDF 추출은 범위 밖. 통과 시험: `docs/image-plan-acceptance.md` |
| 별도 에이전트 (Agent SDK) | 사내 전용 프롬프트·툴·권한을 고정한 실행 환경 | 2단계 뒤 판단. 그전까지 Claude Code와 Claude 앱이 맡는다 |
| 검토·수정 UI (`src/ui`, `ui/web`) | AI 명세(spec JSON)를 기준 도면 위에 그린다. 명세 객체와 기존 도면 객체(핸들)를 가리켜 메모를 남긴다(`review/notes.json`). 값과 배치를 직접 고쳐 명세에 저장한다. CAD(COM)에 붙지 않는다 | 지금. 본인 시범 뒤 직원에게 넓힌다 |
| ArcAid 웹 통합 | 엔진과 IR을 웹 서비스에서 사용 | 2단계 이후 |

## 사내 도입 순서

본인 실무로 먼저 검증하고, 반복 작업이 툴로 굳은 뒤 직원에게 넓힌다.

1. 본인 실무 건에 적용해 검증한다.
2. 반복 작업 2\~3개를 고수준 툴로 굳힌다.
3. 직원 1\~2명에게 시범 적용한다. BricsCAD 환경은 동료 PC 검증과 함께 확인한다.
4. 스킬과 MCP를 사내 플러그인으로 묶어 배포한다. PC별 설정은 `config.local.json`으로 나눈다.

배포 전에 운영 규칙을 정한다. AI 결과물은 담당자가 확인한 뒤에만 쓴다. 사용 비용 기준도 이때 정한다. 건축주 도면을 외부 AI로 보내는 범위는 그보다 앞서, 실무 도면을 쓰기 전에 정한다.

## 리스크와 대응

가장 큰 리스크는 혼자 개발하면서 범위가 넓어지는 것이다. 단계마다 통과 기준을 두고, 멈춰도 쓸모 있는 결과를 남기는 것으로 대응한다.

| 리스크 | 대응 |
| --- | --- |
| 혼자 개발하며 범위가 넓어짐 | 단계별 통과 기준을 지키고, 2단계는 첫 사례 1건으로 한정 |
| AI 결과가 매번 다름 | 생성·검사를 엔진 코드로 옮기고, 검사 통과를 완료 조건으로 둔다 |
| 위반 0을 검토 완료로 오인 | 검사하지 못한 항목을 함께 보고하고, 담당자 검토를 생략하지 않는다 |
| DXF 변환 손실(한글, 주석 축척 치수, 레이아웃) | DXF는 중간 형식으로만 쓴다. R2013 이상, 템플릿 DXF에서 생성, 왕복 테스트 통과를 채택 조건으로. 실패한 객체는 CAD 직접 조작 |
| 기존 도면 손상 | 추가와 변경 목록 적용만 한다. 적용 직전 확인, 중복 실행 방지, 실패 시 되돌리기, 수정 전 사본 보관 |
| IR과 CAD 수동 편집의 충돌 | DWG를 형상 기준으로 두고, 엔진 객체는 XDATA 태그로 구분한다. 충돌하면 적용을 멈추고 보고 |
| 표준을 따르지 않은 기존 도면 | 0단계는 표준 레이어 도면만 판독한다. 이후 레이어 대응표로 정리하고 사람이 확인 |
| 다른 직원이 연 파일, 깨진 Xref 경로 | 수정 전 파일 잠금 확인, Xref 상대 경로 통일 |
| 건축주 도면의 외부 전송 | 실무 도면을 쓰기 전(0단계 착수 전)에 사무소 허용 범위를 정한다 |
| 결과물 책임 | 담당 건축가가 확인한 뒤 사용하고, 가정한 값은 매번 보고 |
| CAD 종류·버전 차이 | GstarCAD 2021을 기준으로 하고, BricsCAD는 호환 테스트로 관리 |
